# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Kartis is a personal ticket-reseller toolkit with two halves that share code but boot from separate entry points:

- **Full dashboard mode** (`app.py`) — Flask UI on :5000. Scrapes Lysted / Viagogo / CrowdVolt by attaching to a manually-logged-in Chrome instance over CDP; imports JeruJam Excel exports; tracks expenses, maaser, and profit; runs the Ticketmaster/Kupat/Tickchak drop checker. Requires a desktop with Chrome.
- **Watcher-only mode** (`watcher_only.py`, supervised by `supervisor.py`) — headless drop-checker daemon. No Flask, no Chrome, no browser deps. Designed for an always-on home server. The supervisor `git pull`s every 5 min and restarts the watcher when commits land.

Both share `kartis.db` (SQLite), `db.py`, `notify.py`, and the per-source drop-checker modules. **Only one machine should hold each watcher** — both modes poll independently and would produce duplicate Discord pings.

## Architecture

### Drop-checker source plugins

Each ticketing site is a module exposing a fixed interface; sources are registered in a `SOURCES` / `WATCHER_SOURCES` dict in `app.py:36`, `watcher_only.py:36`, and `add_watcher.py:27`. **To add a new site, write one module and add one row to those three dicts.** Required functions:

- `parse_url(url) -> (event_code, perf_code)` — also accepts shorthand `EVENT/PERF`
- `perf_url(event_code, perf_code) -> str`
- `fetch_selectable_seats(event_code, perf_code) -> list[dict]`
- `seat_key(seat) -> hashable` — what gets diffed between ticks
- `get_labels(event_code, perf_code, lang="iw", missing_block=None)` — Hebrew section names + ILS prices, cached under `tm_cache/`
- `event_summary(labels) -> str`

URL → source detection lives in `_detect_source` in `app.py:43` and `add_watcher.py:30` (identical logic; keep in sync). Bare numeric shorthand `1358/51596` routes to kupat; alpha-prefixed `MBP19/001` routes to ticketmaster; bare slug `mada26` routes to tickchak. Barby is matched on the `barby.co.il` host only — a bare show id like `5086` is indistinguishable from a tickchak slug and routes to tickchak, so paste the full URL. `discover.ticketmaster.co.il` must be tested BEFORE the `ticketmaster.co.il` rule (it would otherwise swallow the discover host); a bare series slug like `next2026` is indistinguishable from a tickchak slug, so paste the full URL (or the `discover/<slug>` shorthand).

`ticketmaster.py` and `kupat.py` are pure HTTP (anonymous JSON APIs, no login). `tickchak.py` is similar. None of these go through Chrome.

`kupat.py` is the exception that DOES need Chrome: its `seats-status` endpoint 403s any out-of-page fetch, so seats are harvested by capturing the booking SPA's own XHR (~5-10s/check). Two kupat traps are documented at length in its module docstring — the SPA ignores the `prsntId` URL param (you must click the date row), and `isGA` is an int, not a bool. Read it before touching that module.

`dice.py` (dice.fm, EDM/US) is pure HTTP: the anonymous `api.dice.fm/events/<24-hex id>/ticket_types` endpoint exposes per-type prices, status, and the current price TIER — but NO remaining counts. The internal id is resolved once from the event page's `dice://open/events/<id>` meta tag and cached in `tm_cache/dice_ids.json`. One pseudo-seat per on-sale type, key encodes (name, tier, price), so restocks/new types/tier jumps ping and sell-outs are silent removals. Also a manual /market source (paste a dice.fm URL on the page; currency USD, no velocity — like zappa). Separately, `dice_email.py` + a dice branch in `mail_intake.run_intake` auto-record forwarded DICE purchase/transfer-out emails into `dice_purchases`/`dice_transfers` (per-account holdings ledger on /dice; transfers FIFO-match purchases by the email's dice.fm/event/`<slug>` link; DICE emails omit the event year — it's inferred from the email date; login codes and incoming "sent you tickets" mail are ignored).

`barby.py` (barby.co.il, Tel Aviv club) is pure HTTP and status-only: Barby publishes no seat map and no reliable tickets-left (`sold` can exceed `nochair_max_buy`), so a show is tracked as ONE status-encoded pseudo-seat driven by the `isSoldOut` bool from `/api/shows/show/<id>` — sold-out→on-sale adds a `GA available` seat (routes to `drops`), the reverse routes to `status`. perf_code is always `0`. Don't confuse it with `barby_events.py`, which watches the *catalog* for new shows.

`tm_discover.py` (discover.ticketmaster.co.il — TM-IL's marketing landing page per big multi-date production, e.g. `/event/next2026`) is pure HTTP and status-only: ONE watcher covers the whole SERIES. The page's own uncached JSON (`GET /public/v1/pages/<slug>`, ~13KB; the `<script id="discover-bootstrap">` blob on the HTML page is the same payload behind a 60s CDN cache and is used only as a fallback) lists every date with the status box the page paints — `sold_out` / `no_tickets` / `soon` (gray, not buyable) vs `low_availability` "כרטיסים אחרונים" (orange) / `onsale` "כרטיסים" (green) / `new_event`, where a **null `sale_status` means on sale** (the SPA defaults it). A pseudo-seat is emitted only for BUYABLE dates with the status text riding in the `block`, so the plain add/remove diff pings exactly on gray→orange/green (and on orange↔green, a real supply move) while a date selling out is a silent removal — a 14-date series would otherwise ping twice per flip. Seats are deliberately *physical* (no `ga` flag) for the same reason haku's are: a GA-flagged set collapses to one status line in `notify.py`, hiding WHICH date opened, and only physical seats get the per-seat cool-down that damps a date flapping at TM's low-availability threshold. `perf_code` is always `0`; `meta.firstPerfMs` is the series' LAST date so `_purge_past_watchers` can't reap the watcher on opening night. Worth having even though the drop checker already covers TM performances: it's one request for all dates, it needs no seat map (a sold-out perf has nothing to poll), it picks up dates TM adds later, and it sees the entries TM lists with `eventcode: null` (two of NEXT's Jerusalem dates), which no other checker here can watch.

`haku.py` (hakuapp.com — race registration; built for the sold-out 2027 Houston Marathon) is pure HTTP with two pseudo-seat kinds: one per card on the server-rendered `events.hakuapp.com/events/<key>/registration_options` page (the seat key hashes the card's free text, so any wording change — e.g. the "sold out" notice disappearing — pings with the new text in the seat line), and one per charity that currently has Run-for-a-Reason entries for a watched distance (`RFAR_DISTANCES` = Marathon + Half; the anonymous `beneficiaries_search` POST with `is_available_for_registration=true` + `event_sub_types[]` — ids 1=5K, 4=Half, 5=Marathon — genuinely discriminates per distance). All seats are deliberately *physical* (no `ga` flag): the mixed-venue GA strip would otherwise mute card pings whenever a charity seat exists, and the per-seat cool-down damps a charity flapping at the last-spot boundary. Everything routes to `drops` with a 🏃 headline (source-gated in both tick impls, like dice's). Traps: the Rails backend answers **406 without an `Accept` header**; an empty charity search returns a recognizable no-results fragment and anything unrecognizable raises (a blocked response must never fake "nothing available"); `firstPerfMs` stays `None` so `_purge_past_watchers` never reaps the watcher. Any `*houstonmarathon.com` URL maps to the hardcoded 2027 event key (`HOUSTON_EVENT_KEY`); bare 20-hex shorthand is a haku key (24-hex is DICE).

### US EDM event trackers (posh / leap / eventim / shotgun / tao)

Pacha watches a whole venue CATALOG; this watches **named events** on several ticketing platforms. The poll list is data, not code — it lives in `edm_tracked_events` and is managed with `python edm_events.py --add "<url>"`, `POST /api/edm/add`, or the "Track" box on **/edm**. To support another platform, write a module exposing `SOURCE_NAME` / `parse_url(url)` / `fetch_event(key)` and add one row to `SOURCES` plus one to `_HOST_HINTS` in `edm_events.py` — nothing else in the stack changes (shotgun was added exactly this way).

**`tao` is the exception: it fills its own poll list.** A module in `CATALOG_SOURCES` also exposes `discover() -> (entries, errors)`, and `edm_events.sync_catalogs()` reconciles what it finds into `edm_tracked_events` — adding newly announced shows, pruning the ones that have happened. That makes it a pacha-style venue watcher riding the EDM stack's diff/ping/dashboard plumbing. Rules that matter:
- Auto-added rows carry `auto_source = "<source>:<venue_key>"`; **hand-added rows (NULL) are never pruned**, and a catalog re-finding a hand-added event doesn't make it prunable.
- **Deleting an auto row is futile** — the next sync re-adds it. Pausing is how you silence one, so the sync passes `unpause=False` (a hand `--add`/`POST /api/edm/add` still un-pauses).
- A source whose `discover()` reported **any** venue error does not prune that cycle: a calendar that 500s looks exactly like "no upcoming events", and pruning on that would untrack the whole venue.
- The first tick that stores state for a catalog source is a **silent baseline** — its whole listing lands at once and is backfill, not news. `app.py:_edm_baseline_sources` decides this from `edm_seen_events` (not from the sync's bookkeeping), so it stays right if the list was seeded by a manual `--sync-catalogs` or restored from a backup. Every tick after, an unseen event really is newly announced and pings `new`, worded as an announcement rather than "now tracking" (the fetcher sets `catalog: True` on the dict for that).
- The sync runs from the EDM tick but on its own cadence, `KARTIS_EDM_CATALOG_SYNC_MINUTES` (default 10) — a show hits the calendar hours-to-days before its price moves, so re-sweeping the calendars every 2 minutes would be waste.

All fetchers are pure HTTP (no Chrome, so this can run on the VPS) and return the SAME normalized dict — the contract is documented at the top of `edm_common.py`. `edm_common.rollup()` derives `on_sale` / `sold_out` / `min_price` and the **lead tier** (the cheapest BUYABLE tier = the release currently selling, the analogue of pacha's GA release; its price is what climbs and its count is what the low-stock alert watches).

- `posh_events.py` — posh.vip, the richest of the three. Two anonymous GETs: the Next.js flight payload on `/e/<slug>` yields the 24-hex `eventId` (cached in `tm_cache/posh_events.json` for `KARTIS_POSH_META_TTL_SECONDS`, default 6h, so the steady-state tick is one request), then the site's own tRPC endpoint `https://posh.vip/next-bff/events.getEventTickets?input={"eventId":…}` returns per-wave name / `price` (face) / `totalPrice` (all-in) / `quantityAvailable` (**real remaining inventory**) plus `totalTicketsSold`. Traps: the tRPC mount is `/next-bff`, NOT `/api` (which is a different gateway that 404s every procedure in a JSON-RPC envelope); and the waves are **not** in the page HTML at all — the client fetches them on mount, so scraping the HTML only ever finds the ld+json cheapest price.
- `leap_events.py` — events.leapevents.com, a Showclix white-label. One GET; tiers come from the ld+json `offers` ARRAY (name, all-in price, `availability` InStock/SoldOut) and the numeric ids from the `var EVENT = {…}` blob. **No counts**: `api.showclix.com` 401s anonymous callers and nothing public publishes remaining inventory, so this source is status + price only (same deal `zappa_events.py` has with Eventim-IL).
- `shotgun_events.py` — shotgun.live. One GET. Tiers come from the `"deals":[…]` array carrying **`quantityLeft`** (real remaining inventory), plus an event-level `isSoldOut`; the ld+json MusicEvent supplies metadata. Traps: (1) that array is **escaped inside the `self.__next_f.push` flight payload**, so a regex for `"deals":` on the raw HTML finds nothing — decode the payload first (same trick as pacha/posh); an `RSC: 1` header returns it unescaped but isn't needed, and adding `Next-Router-Prefetch: 1` returns a 459-byte stub with no deals at all. (2) **Prices are FACE, not all-in** — the payload says $35 where checkout charges $39.60 (~13% booking fee), and that rate is computed client-side and published nowhere server-side, so this source reports face value and the /edm page marks it with a superscript `f`. Don't hardcode a fee multiplier; a stale one lies. (3) ld+json `startDate` is UTC — use the payload's `startTime` + `timezone` or a Sat 10pm show displays as Sun 2am.
- `tao_events.py` — **Tao Group's Marquee New York + Marquee Skydeck (Edge, Hudson Yards)**, the two venues in `VENUES` (adding another Tao room is one row; the `term_id` is in `window.reactEventsCalender.filters` on any of their venue pages). Two hosts, two halves. *Catalog:* taogroup.com is WordPress and its venue pages render an empty `<div id="react-events">` that the theme's React bundle fills from the site's OWN public route, `GET /wp-json/wp/v2/events?event_venue=<term_id>` — anonymous, no nonce, no challenge, and with `_fields` the whole two-venue sweep is ~20KB. *Prices:* every event's ACF `links[]` carries a `tickets.taogroup.com/e/<slug>/tickets` URL (an "eventservice" white-label, CakePHP + Stripe) whose server-rendered rows carry the tiers; that slug is the `event_key`. GA sells in numbered releases ("General Admission - Tier 1" → "Tier 2" → …) so the headline price steps up exactly like pacha's ladder — that step is the `price_up` → **jumps** ping this source exists for. Skydeck adds a parallel "GA Fast Pass" and sometimes "Mastercard VIP". Traps: (1) **the ticket page's ld+json `offers` array is not the live state** — every tier reads `availability: InStock` even on a fully sold-out show, its prices are FACE, and it lists rows the page doesn't sell (future releases plus $0 "Guest List" holds that would win the cheapest-tier slot); it is read for name/start/venue ONLY. (2) Both price flavours are published and the page headlines **all-in** (`data-default-all-in-price-each`) with face alongside (`data-default-price-each`) — never reconstruct one from the other, the fee is a flat $5 in most rooms but ran as a percentage ($13.88 on $100) on one Skydeck show. (3) `not-available-sold-out` (genuinely gone → `sold_out`) and `not-available-inactive` (exists but sells elsewhere, e.g. a SevenRooms table → `closed`) mean different things; conflating them reports a table upsell as a sell-out. (4) **Parse only inside `#ticket-types-content`** — the access-code flow ships the JS template that *builds* ticket rows and it contains the same `ticket-type-item` markup as a string. (5) No inventory: the quantity `<select>` tops out at the per-order limit and the limit itself is unpublished, so `available` stays None except at 0. Events that sell only through SevenRooms / speakeasygo have no tickets.taogroup.com link and are skipped — nothing to watch.
- `eventim_events.py` — wl.eventim.us (Eventim USA white-label; the tracked event sells through The Concourse Project). One GET, server-rendered HTML parsed with regex. **Two traps, both of which silently produce a wrong answer rather than an error:** (1) Cloudflare answers **403 to the short "UA + Accept" header set** the other pure-HTTP modules here use — it passes only with the full Chrome set (sec-ch-ua + Sec-Fetch-\* + Upgrade-Insecure-Requests), which is why `edm_common.BROWSER_HEADERS` exists; the 403 body is a 670KB challenge page, so a lax parser reports "0 tiers" instead of "blocked". (2) **`?afflky=<key>` is load-bearing** — the same event id fetched without it returns a 41KB page with NO ticket types, which looks exactly like "everything sold out", so the affiliate key is part of the event identity and `event_key` is `"<id>@<afflky>"`. Inventory: Eventim publishes no counts, but the quantity `<select>`'s highest option is `min(remaining, per-order limit)`, so `max_qty` becomes a real count once a type drops under the limit — exposed as `available` **only** when strictly below it.

**Counts are asymmetric and `None` means UNKNOWN, never zero.** Only posh and shotgun publish real inventory (leap and tao publish none; eventim leaks a tail count). Every diff in `app.py:_edm_diff` is guarded on both sides being known, so a source that publishes no count can never fake a price move, a low-stock crossing, or a sell-out; `low_stock` therefore effectively only fires for posh and shotgun — never for tao. Unit tests for all of this live in the diff cases exercised during development — the guards are the whole point, don't remove them when refactoring.

Ping kinds (`notify.notify_edm_event`), routed like pacha's: `price_down` and `restock` (was fully sold out, now buyable) are the perishable ones → **shocks** channel with a plain-text `content` so the phone push shows the headline; `price_up` and `low_stock` → **jumps**; `soldout` → **status**; `new` (first fetch of a newly tracked event), `onsale` and `new_tier` (a wave that was never listed before appeared) → **new_events**. Pings are sorted perishable-first so a burst can't push a price drop past `EDM_MAX_PINGS_PER_TICK` (12).

State: `edm_tracked_events` (the poll list), `edm_seen_events` (latest state per event + `sold_cum`, the lifetime sold accumulated from availability drops with increases clamped out, exactly like pacha's), `edm_release_log` (one row per wave/tier from first sighting to sell-out — the supply-side history the live pages discard). A per-event fetch failure is recorded in `edm_seen_events.last_error` and **does not** abort the other events or overwrite their last good state. The tick also feeds /market (a `market_events` row + availability snapshot per event, source = `posh`/`leap`/`eventim`/`shotgun`/`tao`, currency USD) throttled to `KARTIS_EDM_MARKET_SNAPSHOT_MINUTES` (default 10).

### Drop-check tick

The per-watcher diff-and-notify cycle is implemented twice — once in `app.py` (as `_check_one_watcher` / `run_tm_check`) and once in `watcher_only.py` (`check_one` / `tick`). Logic is intentionally parallel: fetch seats, diff against `tm_seat_state` rows in the DB, store new state, apply user filters via `filters.py`, notify via `notify.py`, log a drop row. Baseline ticks (first check ever for a watcher) suppress notifications. **If you change the tick logic, update both implementations.**

Notification gating order (both implementations): per-watcher `paused` skips entirely → `master_paused` global skips entirely → filters (`filters.apply`) drop unmatched seats → per-seat cool-down drops recently-pinged physical seats → `master_muted` / per-watcher `muted` / empty `notify_channels` skip sending but still log to `tm_drops`.

Per-seat cool-down: some venues (kupat VIP seats especially) flap a hot seat in and out of the buyable feed every few minutes as it cycles through carts/holds, so the plain add/remove diff would re-ping the same seat all day. After a physical seat pings we stamp `(watcher, seat_key)` in `tm_seat_cooldown` and suppress further pings of that exact seat for `KARTIS_SEAT_COOLDOWN_MINUTES` (default 30; 0 disables). Status pseudo-seats (GA/festival/DICE flips) are never cooled down. The window is anchored to the last *actual* ping, so a seat that keeps flapping pings at most once per window. Cool-down can only remove seats from a notification, never add — worst case it's a no-op. (Implemented in both `app.py._check_one_watcher` and `watcher_only.py.check_one`; helpers `db.tm_seat_cooldown_active` / `tm_seat_cooldown_mark`.)

### Lysted / Viagogo / CrowdVolt scraping (full mode only)

`scraper.py` uses `patchright.sync_api` to `connect_over_cdp("http://localhost:9222")` against the Chrome window launched by `login.py`. **There is no login automation by design** — Cloudflare blocks headless browsers, so a human signs in once and the scraper inherits the session. Chrome's user profile is stored in `./user_data/` (gitignored). If Chrome is closed, all scraping fails until `login.py` runs again.

### Viagogo auto-pricer (full mode only)

`viagogo_pricer.py` keeps opted-in listings just under the cheapest competitor for the same event + section (default undercut $0.04, setting `pricer_undercut`). Runs every 15 min from `app.py`'s scheduler (`run_pricer`; `KARTIS_PRICER_INTERVAL_MINUTES`) — **never add it to watcher_only.py** (needs the CDP Chrome). Controls live on the /sources dashboard (per-listing AUTO + FLOOR, master + dry-run toggles); config/audit in `viagogo_pricer_config` / `viagogo_pricer_log` (the scrape mirror `viagogo_listings` stays pure). All prices USD. Key empirical facts (public URL discovery via homepage search → groupedsearch JSON, the `index-data` script blob on event pages, buyer-currency `rawPrice` + per-event fx calibration from our own listing, price writes via the row's edit modal — the raw SaveListing form-replay fails validation) are documented in the module docstring — read it before touching pricing or edit logic. Safety: master kill switch + dry-run default ON, per-listing floors, lower-only (raise is double-flagged off), a sliding-window drop cap (`pricer_max_drop_pct`, default 15% per `pricer_drop_window_hours` 12h — holds + pings when hit), and manual price changes on inv.viagogo pause that listing until resumed from the dashboard. UI lives on /pricer (mobile-friendly; add-to-home-screen works on iPhone).

### CrowdVolt auto-pricer (full mode only)

`crowdvolt_pricer.py` mirrors the viagogo pricer for CrowdVolt asks: undercut the cheapest competitor of the same event + **ticket type** (CV has no seat map), default undercut $1 (buyers see integer all-in prices, so a cent cut can round invisible; setting `cv_pricer_undercut`). Everything is CV's own JSON APIs called as **in-page fetch()** from a page parked on www.crowdvolt.com through the CDP Chrome (Cloudflare 503s out-of-browser requests) — auth is `Bearer <stytch_session cookie>` + `x-fingerprint-id` (localStorage) + `x-pokedex` headers, all read live from the page. Key endpoints: `buy_sell_history/sell_active` (our asks), `what.crowdvolt.com/api/book/get?event_uqid=` (ALL sellers' asks; our rows matched by `uqid` == our ask_uqids), `market/edit_sell {ask_uqid, price, qty}` (the price write — no UI clicking at all). The SPA sometimes closes duplicate tabs; `CvSession.api` reopens a dead page once per call. Same safety rails as viagogo: master kill switch + dry-run default ON, mandatory floors, lower-only, 15%/12h sliding drop cap, manual changes adopted as baseline. ### Flask + APScheduler

`app.py` is a single ~3500-line Flask module. The scheduler is started at import time (`app.py:3540-3556`) with four jobs:
- `scrape` — hourly Lysted/Viagogo/CrowdVolt pull
- `tm_check` — every `TM_CHECK_INTERVAL_SECONDS` (default 60) drop check
- `mail_intake` — every `KARTIS_INTAKE_INTERVAL_MINUTES` (default 10) Gmail poll for purchase-confirmation emails
- `pacha_events` — every `KARTIS_PACHA_MONITOR_INTERVAL_MINUTES` (default 1) poll of pacha-nyc.com/events (`pacha_events.py`, pure HTTP); Discord-pings new events, waitlist→on-sale flips, GA price climbs, GA/VIP price **drops** (a return or a cheaper earlier release re-opening — kind `price_down`, routed to the `shocks` category / auto-created **#pacha-shocks** bot channel, sorted first under the per-tick ping cap, and sent with a plain-text `content` so the phone push shows the prices; the diff needs `pacha_seen_events.vip_price`, which exists only for this), and low-stock crossings (GA release's tickets-left drops to ≤ `KARTIS_PACHA_LOW_STOCK_THRESHOLD`, default 20; re-arms per release); pings include per-tier "N of M left" counts. State in `pacha_seen_events` (incl. `ga_release`/`ga_available` for the crossing detection). The tick also feeds /market — a `market_events` row (source `pacha`, `currency` USD — the column exists because every other source is ILS) + an availability snapshot into `tickchak_sales_snapshots`, so Pacha rows get the same sold-per-window velocity — but throttled to `KARTIS_PACHA_MARKET_SNAPSHOT_MINUTES` (default 10) so the 1-min poll doesn't 10x the snapshot series; note pacha tier counts are per-RELEASE, so a new release opening raises `available` (the velocity clamp ignores increases). Runs on the VPS — exactly one machine may enable it (`KARTIS_PACHA_MONITOR_ENABLED=0` on the PC) or Discord double-pings. Manual tick: `POST /api/pacha-events/run-now`; status: `GET /api/pacha-events/status`. Dedicated dashboard: **/pacha** (`templates/pacha.html` + `GET /api/pacha`) — tiles, per-release GA counts, click-to-expand tier breakdowns (stored per tick in `pacha_seen_events.tiers_json`), velocity windows, Σ sold.
- `edm_events` — every `KARTIS_EDM_MONITOR_INTERVAL_MINUTES` (default 2) poll of the tracked US EDM events (`edm_events.py`, pure HTTP), which also runs the venue-catalog sync (`tao_events`: the Marquee NY + Marquee Skydeck calendars) every `KARTIS_EDM_CATALOG_SYNC_MINUTES` (default 10) so newly announced shows start being watched on their own. See the "US EDM event trackers" section below. Same single-machine rule as pacha (`KARTIS_EDM_MONITOR_ENABLED=0` on the PC). Manual tick: `POST /api/edm-events/run-now`; status: `GET /api/edm-events/status`; dashboard **/edm**.
- `il_events` — every `KARTIS_IL_EVENTS_INTERVAL_MINUTES` (default 10) poll of the kupat.co.il, ticketmaster.co.il, and barby.co.il event listings (`kupat_events.py` / `tm_events.py` / `barby_events.py`, pure HTTP); Discord-pings new events plus listed→on-sale flips (barby has no pre-sale listing state); state in `site_seen_events`. Kupat and TM additionally get a per-date diff and ping **'newdate'** when a new performance appears under an already-known event page — the listing-feed diff alone can't see extra dates because the event key doesn't change and it only carries the first/closest date. Per-date data comes from each source's `fetch_presentations(events)`: kupat = the site-wide `/api/presentations/` catalog in one call (plain urllib works, gzip required — the same feed market.py reaches via BrowserSession); tm = one `getPerformanceList` request per homepage EVENT row (GROUP rows skipped — members appear as their own events; a per-event fetch error omits the key, which the diff skips — never an empty list, or a blip would fake an empty baseline and flood next tick). Known perf ids live in `site_seen_events.perfs_json` (kupat/tm rows; NULL on barby) as a grow-only union so a date dropping off the feed can't re-ping on return; a NULL `perfs_json` (first tick after deploy) baselines silently. Kupat's on-sale signal = promotion to the www.kupat.co.il WordPress homepage (tiles matched to catalog features by normalized urlName/name; the tile banner rides along as the Discord embed image) — the catalog itself often lists events days before the sale is official, which is exactly what the 'new' ping is for. `on_sale` is a one-way latch in `run_il_events` so homepage rotation can't re-fire 'onsale' pings. Barby's feed is `barby.co.il/api/shows/find` (whole catalog; Cloudflare blocks curl's TLS fingerprint but plain urllib with browser headers passes — a CF challenge surfaces as a JSON-parse error, never as an empty catalog). Kupat's feed is `tickets.kupat.co.il/api/features` (the whole catalog; unlike the seats endpoints it answers plain urllib). TM's feeds are the homepage `getAllTopEvent`/`getSpotLightData` wbtxapi endpoints; sale status is resolved lazily per event from the perf-list status strings (**not** the `active` flag, which lags — see `tm_events._SALE_OPENED_STATUSES`; sold-out counts as "sale opened" so this monitor never overlaps the drop checker's soldout→selling pings). Same single-machine rule as pacha (`KARTIS_IL_EVENTS_ENABLED=0` on the PC). Manual tick: `POST /api/il-events/run-now`; status: `GET /api/il-events/status`.
- `market_sweep` — every `KARTIS_MARKET_INTERVAL_MINUTES` (default 60) market-wide availability sweep (`market.py`) feeding the /market page: every kupat presentation (site-wide `/api/presentations/` catalog + parallel in-page detail fetches through one `kupat.BrowserSession` — the CDN only challenges page loads, so in-page `fetch()` is cheap), every TM-IL homepage event's performances (buyability gated on the perf-list status strings, NOT `getPerformanceDetail.salesOptions`, which returns 0 for everything as of 2026-07), manually-added tickchak events/hubs (`market_manual` table; no global tickchak catalog exists), and the whole zappa-club.co.il catalog (`zappa_events.py` — Eventim-IL white-label; Akamai blocks direct HTTP *and* headless Chromium, so it runs a headful off-screen window; Eventim publishes no ticket counts, so zappa rows are status + from-price only). Because only this machine can fetch zappa, its new-event/on-sale Discord pings fire from the sweep itself (`site_seen_events` source `zappa`), NOT from il_events. Latest state in `market_events`; availability history goes into `tickchak_sales_snapshots` under the same `(source, event_code, perf_code)` keys the watcher-fed `sales_sync` uses, so watched events share one denser series and the page reuses `_sales_windows`. **The sweep never writes `site_seen_events` for kupat/tm** — pre-seeding would swallow the il_events new-event pings. Needs patchright Chromium (kupat), so it runs on the dashboard machine; `KARTIS_MARKET_ENABLED=0` elsewhere. No notifications. Manual tick: `POST /api/market/run-now` (synchronous, ~2 min); status: `GET /api/market/status`; manual tickchak add: `POST /api/market/add {"url": ...}`.
- `vgsales` — every `KARTIS_VGSALES_INTERVAL_MINUTES` (default 30) viagogo market-SALES tracker (`viagogo_market_sales.py`) feeding the **/vgsales** page: one `MarketDataV3` POST per tracked event (every event we hold a fresh listing on + the `viagogo_sales_watchlist`) captures the magnifier popup's "past ten sales" grid — ALL sellers' sales, USD per ticket, works for events we're not listed on. The rows carry NO dates and NO ids (identical rows are common), and the USD prices are display quotes re-computed at the current fx rate (~0.4% overnight drift — price must NEVER anchor row identity), so newness is decided by aligning the ordered window against the previous tick's (`viagogo_sales_events.window_json`) on price-less keys (`_rkey`; a same-order window with only prices moved = mode `repriced`, nothing new); an event's first-ever window is stored as `baseline=1` rows that velocity windows ignore (age unknown); a sale's `observed_at` = the tick that first saw it. Sales land in `viagogo_market_sales` (90d prune, `KARTIS_VGSALES_RETENTION_DAYS`). The pricer's own MarketDataV3 fetch piggybacks into the same ingest (`viagogo_market_sales.ingest_window`), giving pricer-enabled events 15-min resolution, and the tick skips events fetched within interval/2 — the run-now button forces past that. Needs the CDP Chrome, so dashboard machine only (`KARTIS_VGSALES_ENABLED=0` elsewhere). No notifications in v1. Manual tick: `POST /api/vgsales/run-now` (synchronous, forced); status: `GET /api/vgsales/status`; watch/unwatch: `POST /api/vgsales/watch {"url": ...}` / `POST /api/vgsales/unwatch {"event_id": ...}`.
- `backup` — daily 03:00 sqlite copy to `KARTIS_BACKUP_DIR`

Each runner uses a threading lock as a poor-man's mutex so the scheduler can't stack overlapping runs. State dicts (`_last_run`, `_last_backup`, `_last_jerujam`, etc.) at the top of `app.py` back the `/api/*/status` endpoints. `app.run` uses `use_reloader=False` because the scheduler would double-fire under the reloader.

### Database

`db.py` defines the full schema and helpers. SQLite file is `kartis.db` in the repo root, not committed. Tables fall into three buckets:

- **Inventory + sales** — `inventory`, `lysted_purchases`, `viagogo_listings`, `inventory_hidden`, `inventory_unsold`, `sales_hidden`, `sales_canceled`, `event_group_merges`. Populated by `scraper.py` and `import_jerujam.py`. Only `app.py` touches these. (Market-wide viagogo sales — other sellers' sales, not ours — live separately in `viagogo_market_sales` / `viagogo_sales_events` / `viagogo_sales_watchlist`, fed by `viagogo_market_sales.py`.)
- **Drop watchers** — `tm_watchers`, `tm_seat_state`, `tm_drops`. Both `app.py` and `watcher_only.py` write here. **If both run against the same file you'll hit `database is locked` errors** — run only one per machine.
- **Settings** — key/value via `setting_get_bool` etc.; flags like `master_paused`, `master_muted`.

### Auto-update flow (watcher-only mode)

`supervisor.py` is the single binary Task Scheduler launches at boot. It spawns `watcher_only.py` as a child, runs `git pull --ff-only` every `KARTIS_PULL_INTERVAL_SECONDS` (default 300), and on new commits: terminates the child → `pip install -r requirements.txt` → restarts. Crash backoff is exponential up to 1h. The remote needs to be set up so the first manual `git pull` succeeded — after that Git Credential Manager handles automated pulls.

## Conventions worth knowing

- Seat dicts use mixed key naming: normalized (`block`, `row`, `seat`) for kupat and newer ticketmaster code; raw (`b`, `r`, `l`) for older ticketmaster fixtures. Helpers in `notify.py` (`_seat_block`, `_seat_row`, `_seat_num`) accept both — if you add code that reads seat fields, accept both forms.
- Discord notifications route per category to separate channels via optional `DISCORD_WEBHOOK_DROPS` / `_STATUS` / `_NEW_EVENTS` / `_JUMPS` / `_SHOCKS` / `_PRICER` / `_LISTINGS` / `_TODOS` env vars (see `_WEBHOOK_ENV` in `notify.py`); any category without its own webhook falls back to `DISCORD_WEBHOOK_URL`. New notification kinds should pick a category (or add one) rather than reading `DISCORD_WEBHOOK_URL` directly. `shocks` (pacha price drops, plus EDM price drops and restocks) resolves specially: explicit `DISCORD_WEBHOOK_SHOCKS` → bot-created `#pacha-shocks` channel (`_pacha_shocks_webhook` in `notify.py`) → main webhook. Within `notify_drop`, alerts whose added seats are all non-buyable status pseudo-seats (sold out / last tickets / closed) route to `status`; anything actually buyable routes to `drops`. Additionally, a watcher with a `discord_channel` name sends its buyable-drop pings to a per-event channel instead: `discord_bot.py` lazily creates the channel + webhook via a bot (`DISCORD_BOT_TOKEN` + `DISCORD_GUILD_ID`, optional `DISCORD_DROPS_CATEGORY_ID`; cache in `discord_event_channels`), new watchers default to a dateless slug of their label (`slugify_label`) so multi-date shows share one channel, and any bot failure falls back to the shared drops webhook. Status pings never use per-event channels.
- All persisted timestamps are UTC ISO-8601 (`datetime.now(timezone.utc).isoformat()`).
- Watcher IDs are `tmw-<12 hex chars>` (`add_watcher.py:63`).
- `KARTIS_ATTACHMENTS_DIR` defaults to `./attachments` inside the repo — and the repo lives in OneDrive on the main PC, which is the intended cloud backup for ticket PDFs.
- The repo's working directory itself is inside OneDrive (`C:\Users\13pin\OneDrive\Documents\GitHub\2.0`), so writes can be picked up by OneDrive sync.
